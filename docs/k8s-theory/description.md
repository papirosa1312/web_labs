# Практична робота 9: Теоретична схема Kubernetes-додатку

## 1. Обраний сервіс
Для моделювання обрано бекенд-сервіс **Music Store API** (`music-store-api`, Node.js + Express + SQLite) з нашого командного проєкту. Він надає REST API для перегляду каталогу музичних інструментів та оформлення замовлень. Основні користувачі — покупці інтернет-магазину (через веб-клієнт) та адміністратори каталогу.

## 3. Опис архітектури та шляху трафіку
Сервіс `music-store-api` розгортається в окремому namespace **`music-store-prod`** усередині Kubernetes-кластера. Зовнішній трафік від клієнта через DNS (`api.music-store.local`) потрапляє на **Load Balancer**, далі на **Ingress**, який маршрутизує запити за хостом і шляхом `/api` до внутрішнього **Service** (`music-store-api-svc`, тип `ClusterIP`), а той рівномірно розподіляє їх між **Pod-ами**. У Deployment закладено **2 репліки (Pod-и)** для базової відмовостійкості та оновлення без простою (якщо один Pod впаде, інший продовжить обробляти запити). Доставка коду відбувається автоматично: після `git push` у репозиторій `github.com/papirosa1312/web_labs` пайплайн **GitHub Actions** проганяє тести, збирає Docker-образ і пушить його в **Container Registry** (`ghcr.io/papirosa1312/music-store-api:1.0.0`), звідки Kubernetes Deployment завантажує образ під час старту Pod-ів.
